# P2P-кооп (netplay)

Два инстанса лаунчера в одной LAN играют одну NES-игру вместе — один хостит,
другой подключается. Этот документ описывает протокол и архитектуру; UI —
см. [screens.md](screens.md) (`Netplay Lobby Screen`, `Emulator Screen`,
вкладка «Сеть» в `Settings Screen`).

## Явные ограничения MVP

- Ровно два игрока: хост = NES-контроллер 1, клиент = NES-контроллер 2.
- Только LAN (UDP broadcast-обнаружение) — игры через интернет нет.
- Нет паузы во время кооп-сессии (синхронизировать паузу по сети — отдельная
  задача), нет save/load state (уже отключены как заглушки и в одиночной игре).
- Нет реконнекта после разрыва — обрыв завершает сессию, обе стороны видят
  ошибку и должны заново пройти лобби.
- Оба игрока должны независимо владеть ROM-файлом с одинаковой SHA-256
  чек-суммой (сверяется при рукопожатии) — сам ROM по сети не передаётся.
- Задержка ввода фиксирована (см. ниже) и не настраивается пользователем.

## Почему нельзя переиспользовать jsnes `Browser`

`Browser` (`node_modules/jsnes/src/browser/index.js`) владеет собственным
`FrameTimer`/rAF-циклом и напрямую подключает `KeyboardController`/
`GamepadController` к `nes.buttonDown/buttonUp` — без точки расширения для
внедрения синхронизированного ввода партнёра перед кадром. Поэтому кооп-режим
(`src/netplay/engine.ts`) создаёт `NES` напрямую и сам вызывает `nes.frame()`
в своём цикле, выставляя `nes.buttonDown/buttonUp` для **обоих** игроков
непосредственно перед каждым кадром. `Screen`/`Speakers` (канва и звук)
переиспользуются напрямую из `jsnes/src/browser/screen.js` и `speakers.js` —
это внутренние классы пакета, не экспортированные из `jsnes/src/index.js`,
но пакет уже вендорится/патчится под этот проект (`patches/jsnes+2.1.0.patch`,
версия зафиксирована), так что зависимость от его внутренностей — приемлемый
компромисс.

`NES.toJSON()`/`fromJSON()` существуют, но не сериализуют сами байты ROM —
переноса состояния при подключении нет и не нужен: оба пира независимо
грузят свою копию ROM и стартуют с чистого power-on reset вместе (сверка
чек-суммы при рукопожатии гарантирует, что это один и тот же ROM).

## Синхронизация: лок-степ с фиксированной задержкой ввода

**Главный приоритет — отсутствие рассинхрона важнее плавности.** Оба пира
детерминированно эмулируют один и тот же ROM с одной и той же историей
нажатий кнопок обоих контроллеров ⇒ пока эта история идентична на обеих
сторонах, кадры идентичны. Гарантия идентичности:

Каждый пир держит счётчик кадров `frameNo`. На каждый rAF-тик:
1. Читает своё текущее состояние NES-кнопок (клавиатура + геймпад, см.
   `src/netplay/localInput.ts`) — 1 байт, бит = `1 << Controller.BUTTON_*`
   (0-7; turbo-кнопки 8/9 не участвуют).
2. Буферизует это состояние для `frameNo + INPUT_DELAY_FRAMES` и
   fire-and-forget отправляет партнёру (`{frame, buttons}`).
3. Смотрит буферизованный ввод **партнёра** для ТЕКУЩЕГО `frameNo`. Если ещё
   не пришёл — ничего не делает в этот тик (не продвигается) и пробует
   заново на следующем rAF. Это и есть гарантия: кадр не рендерится, пока обе
   стороны не знают точное состояние обоих контроллеров именно для этого
   номера кадра.
4. Иначе: `nes.buttonDown/buttonUp` для своего игрока (буферизованный
   локальный ввод для `frameNo`) и для партнёра (полученный ввод),
   `nes.frame()`, `screen.writeBuffer()`, `frameNo++`.

`INPUT_DELAY_FRAMES = 6` (~100мс при 60 кадр/с) — захардкожено, не
настраивается. LAN RTT обычно <5мс, Tauri IPC (тот же процесс) — доли мс,
так что в нормальных условиях задержка полностью маскирует сетевой round-trip
и локальная эмуляция не стопорится. При деградации сети (пакет потерян/
задержан) стопорится — это и есть цена гарантии "никогда не разойтись".

## Почему сеть держит Rust, а не webview

Веб-вью не может открывать сырые сокеты. Rust-бэкенд владеет TCP-сессией;
JS вызывает fire-and-forget команду на каждый кадр, чтобы отправить локальный
ввод (`netplay_send_input`), а полученный от партнёра ввод Rust реэмитит в JS
Tauri-событием (`netplay://remote-input`).

## Обнаружение хостов (LAN UDP broadcast)

`src-tauri/src/netplay/discovery.rs`:
- **Хост**: пока хостинг активен, раз в секунду шлёт JSON `HostAnnounce
  {display_name, game_title, rom_checksum, tcp_port}` broadcast'ом на
  `DISCOVERY_PORT = 47998`.
- **Клиент**: слушает этот порт, пока открыт вид «Подключиться» в лобби,
  эмитит `netplay://host-found` на каждый новый/обновлённый анонс и
  `netplay://host-lost`, если анонсов от хоста не было >5 секунд (TTL-чистка).

Приёмный UDP-сокет открывается с `SO_REUSEADDR`(+`SO_REUSEPORT` на Unix) через
крейт `socket2` — это позволяет тестировать хост и клиент двумя окнами на
одной машине (иначе второй `bind()` на тот же порт падал бы с "Address already
in use").

## Протокол сессии (TCP, newline-delimited JSON)

Трафик крошечный (одно `Input`-сообщение на кадр, ~60 раз/сек на игрока) —
JSON проще самодельного бинарного протокола и накладные расходы тут не важны.

```rust
#[serde(tag = "type")]
enum NetplayMessage {
    Handshake { display_name: String, rom_checksum: String },
    HandshakeAck { display_name: String, ok: bool, reason: Option<String> },
    Input { frame: u32, buttons: u8 },
    Disconnect,
}
```

Рукопожатие (`src-tauri/src/netplay/session.rs`): клиент подключается и первым
шлёт `Handshake` со своей чек-суммой; хост сверяет её со своей и отвечает
`HandshakeAck` (при несовпадении — `ok: false` + причина, соединение
закрывается, хост продолжает слушать следующую попытку). После успешного
рукопожатия обе стороны поднимают reader/writer-задачи
(`session::spawn_session`): writer пишет исходящие `NetplayMessage` из канала,
reader эмитит `netplay://remote-input` на `Input` и `netplay://peer-disconnected`
на `Disconnect`/EOF/ошибку чтения — вторая сторона не должна отдельно
опрашивать состояние соединения.

## Tauri-команды и события

Команды (`src-tauri/src/commands/netplay.rs`): `netplay_start_hosting`,
`netplay_stop_hosting`, `netplay_start_discovery`, `netplay_stop_discovery`,
`netplay_join_host`, `netplay_send_input`, `netplay_disconnect`.

События (JS слушает через `src/api/netplay.ts`): `netplay://host-found`,
`netplay://host-lost`, `netplay://client-connected`, `netplay://hosting-failed`,
`netplay://remote-input`, `netplay://peer-disconnected`.

Фоновые задачи (broadcast/discovery/accept/reader/writer) запускаются через
`tauri::async_runtime::spawn` (не голый `tokio::spawn`) — так они выполняются
на рантайме, которым управляет сам Tauri.
