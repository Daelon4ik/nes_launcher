# Мультиплатформенность: Sega Genesis (.gen)

**Статус: сама эмуляция реализована** (движок, видео, аудио, ввод, save state в
`Emulator Screen`, см. «Движок эмуляции» и «Save state» ниже) — можно добавить `.gen`
через «Добавить игры»/сканирование библиотеки и запустить игру. **Остальное — Settings/
Main/Store экраны, метаданные, поле `Game.platform` в БД, кооп — ещё спланировано, не
реализовано** и помечено «планируется» здесь и в перекрёстных ссылках из
[architecture.md](architecture.md), [data-model.md](data-model.md), [screens.md](screens.md),
[store.md](store.md), [netplay.md](netplay.md).

## Идентификация платформы

Полноценного поля `platform` на `Game` пока нет — сейчас платформа определяется на лету по
расширению пути к ROM (`.gen` → Genesis, всё остальное → NES), отдельно в каждом месте,
которому это нужно:

- `src-tauri/src/commands/library.rs::is_supported_rom` — какие расширения вообще
  принимаются при сканировании папки и ручном добавлении файла (`.nes`, `.gen`).
- `src/screens/EmulatorScreen/index.tsx` — `const isGenesis = game.romPath.toLowerCase().endsWith(".gen")`,
  переключает движок/раскладку/save-state кодек.

Это самодостаточно для того, чтобы Genesis-игра запускалась, но недостаточно для
Store/Main-фильтров и выбора раздела метаданных (см. ниже) — там платформу нужно знать
*до* того, как файл ROM уже есть на диске (например, чтобы решить, в каком разделе
emu-land.net искать). Для этого по-прежнему нужно завести `platform: "nes" | "genesis"` на
`Game` (см. [data-model.md](data-model.md)) как источник истины, определяемое по
расширению в момент добавления в библиотеку — план ниже не изменился, просто ещё не
реализован. Только `.gen` — без `.md`/`.bin`/`.smd` (расширенная поддержка форматов —
отдельная задача, если понадобится). Существующие записи `Game` при миграции получат
`platform = "nes"` по умолчанию (все они и так `.nes`) — миграция по образцу
`player_mode` (`add_column_if_missing` в `src-tauri/src/db/mod.rs`).

## Движок эмуляции (реализовано)

NES работает через [jsnes](https://github.com/bfirsh/jsnes) — JS-библиотека прямо в webview,
без Rust-эмуляции (`Browser` из пакета монтируется в `EmulatorScreen`, ROM-байты читает
Rust-бэкенд и просто отдаёт во фронтенд). Genesis — тем же путём: WASM-ядро
[genesis_plus_gx](https://github.com/ekeeke/Genesis-Plus-GX) (libretro-порт того же ядра,
что в RetroArch) в браузере, без нативной эмуляции на Rust-стороне.

**Выбранный пакет: [`romdev-core-gpgx`](https://www.npmjs.com/package/romdev-core-gpgx)**
(часть проекта [romdev](https://github.com/monteslu/romdev)) — публикует только сырой
Emscripten-артефакт ядра (`genesis_plus_gx_libretro.js` + `.wasm`), без обвязки. Это было
осознанным выбором **против** двух других рассмотренных вариантов:

- **EmulatorJS** — готовый цельный веб-плеер (своё меню, свой конфиг геймпада, свой save
  state UI), а не управляемый класс — не даёт пошагово вызывать один кадр эмуляции извне,
  что обязательно для будущего лок-степ кооп-нетплея (см. «Netplay» ниже), и конфликтует с
  уже существующим UI `Emulator Screen` (свой оверлей/слоты). Плюс GPL-3.0 на сам плеер.
- **`romdev-core-host`** (обвязка того же romdev-проекта, дала бы готовый `LibretroHost` с
  `stepFrames`/`setInput`/`serializeState`) — отклонена: её скомпилированный код
  разбросанно дёргает `await import("node:fs/promises")` и подобные Node-only импорты,
  которые ломают продакшен-сборку Vite (Rollup пытается статически резолвить их для
  браузерного бандла). Вместо неё — собственная, компактная (~250 строк) реализация
  публичного libretro callback API (`src/emulator/genesis/callbacks.ts`, `framebuffer.ts`),
  портированная и адаптированная под TS из `romdev-core-host/callbacks.js`+`framebuffer.js`
  (MIT), но без Node-зависимостей и без ненужного для genesis_plus_gx кода (proxied-ядра,
  HW-render, C64-специфика).

**Лицензия ядра**: Genesis Plus GX распространяется под non-commercial лицензией (см.
`node_modules/romdev-core-gpgx/README.md`) — свободно для личного/некоммерческого
использования, запрещает перепродажу. Это ограничение самого движка (не пакета), значимо
только если лаунчер когда-либо станет коммерческим.

**Node → браузер патч**: `genesis_plus_gx_libretro.js` собран с Emscripten-флагом
`ENVIRONMENT_IS_NODE=true` захардкоженным — без патча webview падает на
`await import("module")`. Патч (`patches/romdev-core-gpgx+0.14.0.patch`, тот же
`patch-package`-механизм, что и у `patches/jsnes+2.1.0.patch`) меняет флаг на `false`;
поскольку `GenesisCore.create()` (см. `src/emulator/genesis/GenesisCore.ts`) сам скачивает
`.wasm` через `fetch` и передаёт байты модулю как `wasmBinary` (минуя emscripten-овский
`readBinary`/`readAsync`, которые под `-sENVIRONMENT=node` вообще не собраны для браузера),
остальной код глея не тронут и корректно работает — проверено и под Node (симулированная
браузерная загрузка через явный `wasmBinary`), и вживую в браузере (Chromium через
`agent-browser`, страница гоняла ядро с синтетическим ROM: кадры, звук, save state).

### Диспетчеризация в Emulator Screen (реализовано, без формального интерфейса)

`EmulatorScreen` не получил общий интерфейс движка (`EmulatorCore`) — вместо этого прямое
ветвление по `isGenesis` внутри тех же эффектов, что уже занимались jsnes: отдельная ветка
монтирует `<canvas>` вручную, гоняет `requestAnimationFrame`-цикл (`core.frame()` +
`core.getFrameRgba()` → `ctx.putImageData`), проигрывает звук через `AudioBufferSourceNode`
(накопительное планирование по `audioCtx.currentTime`), слушает клавиатуру/геймпад с
фиксированной раскладкой (см. «Контроллер» ниже) и делает save state через
`core.serializeState()`/`unserializeState()`. `fitScreenPixelPerfect` обобщена на
параметры `(stage, width, height)` вместо захардкоженных NES-констант — Genesis обычно
320×224, но может быть 256×192 (H32-режим), берётся из `GenesisCore.width/height` после
разгонных кадров в `loadRom()`.

Пропущенный сейчас формальный `EmulatorCore`-интерфейс — осознанное упрощение (YAGNI, две
ветки читаемее преждевременной абстракции с одним реальным потребителем на каждую), но его,
скорее всего, придётся ввести, когда дойдёт очередь до кооп-нетплея для Genesis (см. ниже) —
`NetplayEngine` тогда получит вторую реализацию движка тем же способом.

## Контроллер

NES-раскладка (8 экшенов: `UP/DOWN/LEFT/RIGHT/A/B/SELECT/START`, 2 игрока) не покрывает
Genesis-пад. Решение — отдельный набор экшенов на платформу, а не расширение общего:

- **NES** (без изменений): `UP/DOWN/LEFT/RIGHT/A/B/SELECT/START`.
- **Genesis** — 3-кнопочный пад: `UP/DOWN/LEFT/RIGHT/A/B/C/START` (`GenesisButtons` в
  `GenesisCore.ts`). 6-кнопочный пад (доп. `X/Y/Z/MODE`) — опциональное расширение позже,
  не блокирует первую версию.
- **Реализовано, но без настроек**: клавиатура игрока 1 (стрелки, `Z/X/C` → A/B/C, Enter →
  Start) и геймпад для обоих игроков (D-pad → стрелки, кнопки 0/1/2 → B/A/C, кнопка 9 →
  Start) зашиты константой прямо в `EmulatorScreen` (`GENESIS_KEY_MAP` + опрос в отдельном
  `useEffect`) — **не** читаются из `localStorage` и не переназначаются на `Settings
  Screen`, в отличие от NES. `GenesisCore.setInput(port, buttons)` принимает полное
  состояние пада за раз (не down/up-события, как `nes.buttonDown/buttonUp`), поэтому и
  клавиатурный обработчик, и опрос геймпада сами держат текущее состояние кнопок.
- **Спланировано, не реализовано**: платформенный неймспейс в `localStorage` —
  `keyboard_controls_nes`/`keyboard_controls_genesis` (и аналогично `gamepad_controls_*`)
  вместо текущих плоских `keyboard_controls`/`gamepad_controls`, плюс переключатель и
  редактор раскладки на `Settings Screen` (см. ниже). До этого момента раскладка Genesis
  непереназначаема.

## Settings Screen: переключатель nes/gen

Внутри вкладки «Эмулятор» (`EmulatorTab.tsx`) — верхний переключатель-кнопки «NES» /
«Genesis», под которым показываются настройки соответствующей платформы:

- **Общее** (не зависит от платформы, остаётся как есть): громкость (`Settings.volume`
  — общий на все платформы, отдельный per-platform громкости не заводим).
- **Платформо-зависимое**: подвкладки «Клавиатура»/«Контроллер» показывают набор
  экшенов активной платформы (NES: 8 кнопок как сейчас; Genesis: 3-кнопочный набор выше),
  читают/пишут в соответствующий платформенный ключ `localStorage`.

## Store Screen: фильтр и источник для Genesis

- **UI**: переключатель-кнопки «NES» / «Genesis» (тот же паттерн, что уже держим в уме
  для `Main Screen`, см. ниже) — определяет, в каком разделе искать/листать и какое
  расширение ожидается при установке.
- **Источник**: второй раздел на [emu-land.net](https://www.emu-land.net/), по аналогии с
  текущим `NES_SECTION_ID = "13"` / `ROMS_PATH = "/consoles/dendy/roms"`
  (`src-tauri/src/metadata/scraper.rs`, `src-tauri/src/store/scraper.rs`) — нужен второй
  `GENESIS_SECTION_ID` и свой `ROMS_PATH` (сайт называет раздел Sega/Mega Drive/Genesis —
  точный id раздела и путь **не проверены вживую**, нужно уточнить при реализации по
  образцу того, как уже уточнялся `id=13` и `/consoles/dendy/roms`).
- Установка из магазина берёт из архива первый файл с расширением `.gen` (вместо `.nes`)
  для игр Genesis-раздела; остальной пайплайн (`store_install`, дедуп имени, авто-подтяжка
  метаданных постфактум) переиспользуется без изменений, просто параметризуется
  `platform`/секцией.

## Main Screen: фильтр платформы

Переключатель-кнопки «NES» / «Genesis» (как в Store, не выпадающий список) — рядом с
существующим фильтром режима игры (`filterMode`, [screens.md](screens.md#1-main-screen)).
Оба фильтра комбинируются (AND) при построении `filteredGames`. Игры без явного выбора
(«обе платформы сразу») не предусмотрены — ровно одна платформа активна за раз, как и в
Store.

## Метаданные

`metadata/scraper.rs::fetch_metadata` сейчас жёстко ищет по `NES_SECTION_ID`. С
добавлением `Game.platform` поиск метаданных выбирает `SECTION_ID` по платформе игры —
тот же `GENESIS_SECTION_ID`, что заведён для Store выше (один и тот же раздел сайта
обслуживает и поиск ROM'ов, и метаданные, как уже устроено для NES). Парсинг
описания/обложки/`player_mode` (селекторы `.ftext > p`, `.ss-area img`, `.finfo li`)
предполагается платформенно-независимым (общий шаблон страницы сайта) — требует проверки
на реальной странице Genesis-игры при реализации.

## Save state (реализовано)

`SaveState.file_path` для NES — конкретно jsnes-формат (`nes.toJSON()` как JSON). Формат
Genesis-снимка (`retro_serialize`, ~1МБ бинарного блоба — полное состояние 68000/Z80/VDP/
PSG/YM2612) полностью отличается и остаётся непрозрачным для бэкенда: `EmulatorScreen`
кодирует его в base64 (`genesisStateToBase64`/`genesisStateFromBase64` в `GenesisCore.ts`,
чанками по 32КБ — иначе `String.fromCharCode(...bigArray)` падает на лимите аргументов) и
шлёт той же командой `save_state(gameId, slot, data: string)`, что и NES — бэкенд как хранил
произвольную строку файлом на диске, так и хранит, никаких изменений в
`src-tauri/src/commands/saves.rs`/`db` не понадобилось. `SaveState` в БД не получил нового
поля — платформа определяется по `isGenesis` в `EmulatorScreen` (см. «Идентификация
платформы» выше), этого достаточно, чтобы выбрать правильный кодек при загрузке слота.

## Netplay (кооп) — спланировано, не реализовано

Явно вынесено за рамки первой версии эмуляции (см. «Явные ограничения» в начале файла) —
`EmulatorScreen` сейчас показывает ошибку, если открыть кооп-сессию для Genesis-игры
(`netplay && isGenesis` в основном эффекте), вместо попытки скормить Genesis ROM в
NES-движок. `GenesisCore.frame()`/`setInput()` уже имеют ровно ту пошаговую форму (один
кадр за вызов, явное состояние пада), которая нужна лок-степ-движку — технической
блокировки для последующей интеграции нет, просто не сделано в этом заходе.

Сейчас `src/netplay/engine.ts` жёстко завязан на внутренности jsnes: создаёт `NES` напрямую, сам вызывает `nes.frame()`,
переиспользует `jsnes/src/browser/screen.js`/`speakers.js` (см.
[netplay.md](netplay.md#почему-нельзя-переиспользовать-jsnes-browser)). Лок-степ протокол
сам по себе (буферизация ввода, `INPUT_DELAY_FRAMES`, `NetplayMessage`) платформо-агностичен
— завязка только в месте, где движок непосредственно продвигается на кадр и куда пишутся
кнопки. План: `NetplayEngine` дублирует для Genesis то же ветвление, что уже есть в
одиночной игре (см. «Диспетчеризация в Emulator Screen» выше) — `GenesisCore.frame()`/
`setInput()` вместо прямого импорта `jsnes`, вызываемые для обоих игроков так же, как
сейчас `nes.buttonDown/buttonUp`/`nes.frame()`. Если к этому моменту ветвлений накопится
достаточно (одиночная игра + кооп, каждая на 2 платформы), может иметь смысл наконец
формализовать общий интерфейс движка вместо копирования `isGenesis`-веток — решать по
факту, а не заранее.
Требования протокола не меняются — оба пира всё так же должны независимо владеть ROM с
одинаковой SHA-256 (сверяется в `Handshake`), только теперь ROM может быть `.gen`, а не
только `.nes`. Genesis-контроллер (3 или 6 кнопок, см. выше) кодируется в `Input.buttons`
вместо текущего NES-специфичного 1-байтового битового поля — потребует расширения формата
сообщения (например, отдельный `platform`/более широкий `buttons`, чтобы вместить больше
кнопок, чем NES-байт) — уточнить точный формат при реализации.
