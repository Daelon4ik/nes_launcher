# Мультиплатформенность: Sega Genesis (.gen)

**Статус: спланировано, не реализовано.** Этот документ фиксирует дизайн перед началом
работы — код за ним пока не следует. Ссылки из [architecture.md](architecture.md),
[data-model.md](data-model.md), [screens.md](screens.md), [store.md](store.md) и
[netplay.md](netplay.md) помечены как «планируется» и указывают сюда.

Сейчас весь лаунчер жёстко рассчитан на один эмулятор (NES/jsnes) — понятия «платформа»
нет ни в БД, ни в типах, ни в скрапере. Цель — добавить второй эмулятор (Sega
Genesis/Mega Drive, файлы `.gen`), не собирая параллельный лаунчер: платформа — это новое
измерение, которое пронизывает библиотеку, магазин, метаданные, настройки и сам экран
эмулятора.

## Идентификация платформы

Новое поле `platform: "nes" | "genesis"` на `Game` (см. [data-model.md](data-model.md)) —
источник истины для остальных решений (какой движок грузить, какой набор экшенов
контроллера показывать, в каком разделе emu-land.net искать метаданные). Определяется по
расширению файла в момент добавления в библиотеку (сканирование папки, ручное добавление,
установка из магазина):

| Расширение | Platform |
|---|---|
| `.nes` | `nes` |
| `.gen` | `genesis` |

Только `.gen` — без `.md`/`.bin`/`.smd` (расширенная поддержка форматов — отдельная
задача, если понадобится). Существующие записи `Game` при миграции получают
`platform = "nes"` по умолчанию (все они и так `.nes`) — миграция по образцу
`player_mode` (`add_column_if_missing` в `src-tauri/src/db/mod.rs`).

## Движок эмуляции

NES сейчас работает через [jsnes](https://github.com/bfirsh/jsnes) — JS-библиотека прямо в
webview, без Rust-эмуляции (`Browser` из пакета монтируется в `EmulatorScreen`, ROM-байты
читает Rust-бэкенд и просто отдаёт во фронтенд). Genesis — тем же путём, WASM/JS-ядро в
браузере, без нативной эмуляции на Rust-стороне.

**Кандидат: [EmulatorJS](https://emulatorjs.org/) с ядром `genesis_plus_gx`**
(скомпилированный в WASM порт libretro-ядра genesis_plus_gx) — самый зрелый вариант из
рассмотренных (используется массово, ядро genesis_plus_gx — тот же, что в RetroArch).
Отличие от интеграции jsnes: EmulatorJS — это готовый веб-плеер (свой загрузчик, свой
набор `data/*.wasm`/`*.js`), а не импортируемый класс с императивным API вроде
`new Browser({ container, romData })` — понадобится адаптер (`EmulatorScreen` должен
уметь монтировать либо jsnes `Browser`, либо EmulatorJS-плеер, за общим интерфейсом, см.
ниже). Точный npm-пакет/способ вендоринга (аналог `patches/jsnes+2.1.0.patch`) — уточнить
при реализации; альтернативы (`jgenesis`, чисто-JS `Emulatrix`) рассматривались, но менее
зрелые/поддерживаемые для встраивания.

### Абстракция экрана эмулятора

`EmulatorScreen` сегодня напрямую завязан на jsnes (`Browser`, `NES`, `nes.toJSON()`,
`nes.buttonDown`) — ни интерфейса, ни диспетчеризации по платформе нет. Для Genesis
понадобится минимальный слой выбора движка по `Game.platform`:

- Общий интерфейс движка (условно `EmulatorCore`): `mount(container, romData)`,
  `destroy()`, `pause()/resume()`, `saveState(): Blob`, `loadState(Blob)`,
  `setButtonState(player, action, pressed)`, `setVolume(0..1)`.
- Реализация для `nes` — тонкая обёртка над существующим кодом (`Browser`/`NES`), без
  изменения поведения.
- Реализация для `genesis` — обёртка над выбранным ядром (EmulatorJS/genesis_plus_gx).
- Canvas-геометрия перестаёт быть захардкоженной NES-константой (`NES_WIDTH=256`,
  `NES_HEIGHT=240`) — берётся из активного движка (Genesis: 320×224 NTSC).

## Контроллер

NES-раскладка (8 экшенов: `UP/DOWN/LEFT/RIGHT/A/B/SELECT/START`, 2 игрока) не покрывает
Genesis-пад. Решение — отдельный набор экшенов на платформу, а не расширение общего:

- **NES** (без изменений): `UP/DOWN/LEFT/RIGHT/A/B/SELECT/START`.
- **Genesis**, базовый вариант — 3-кнопочный пад: `UP/DOWN/LEFT/RIGHT/A/B/C/START`.
  6-кнопочный пад (доп. `X/Y/Z/MODE`) — опциональное расширение позже, не блокирует
  первую версию.
- Раскладки клавиатуры/геймпада в `localStorage` получают платформенный неймспейс —
  ключи вида `keyboard_controls_nes`/`keyboard_controls_genesis` (и аналогично
  `gamepad_controls_*`) вместо текущих плоских `keyboard_controls`/`gamepad_controls`.
  Существующие плоские ключи при первом запуске после обновления трактуются как
  `*_nes` (одноразовая миграция чтения, без потери текущих привязок NES).

## Settings Screen: переключатель nes/gen

Внутри вкладки «Эмулятор» (`EmulatorTab.tsx`) — верхний переключатель-кнопки «NES» /
«Genesis», под которым показываются настройки соответствующей платформы:

- **Общее** (не зависит от платформы, остаётся как есть): громкость (`Settings.volume`
  — общий на все платформы, отдельный per-platform громкости не заводим).
- **Платформо-зависимое**: подвкладки «Клавиатура»/«Контроллер» показывают набор
  экшенов активной платформы (NES: 8 кнопок как сейчас; Genesis: 3-кнопочный набор выше),
  читают/пишут в соответствующий платформенный ключ `localStorage`.

## Store Screen: фильтр и источник для Genesis

- **UI**: переключатель-кнопки «NES» / «Genesis» (тот же паттерн, что уже держим в уме
  для `Main Screen`, см. ниже) — определяет, в каком разделе искать/листать и какое
  расширение ожидается при установке.
- **Источник**: второй раздел на [emu-land.net](https://www.emu-land.net/), по аналогии с
  текущим `NES_SECTION_ID = "13"` / `ROMS_PATH = "/consoles/dendy/roms"`
  (`src-tauri/src/metadata/scraper.rs`, `src-tauri/src/store/scraper.rs`) — нужен второй
  `GENESIS_SECTION_ID` и свой `ROMS_PATH` (сайт называет раздел Sega/Mega Drive/Genesis —
  точный id раздела и путь **не проверены вживую**, нужно уточнить при реализации по
  образцу того, как уже уточнялся `id=13` и `/consoles/dendy/roms`).
- Установка из магазина берёт из архива первый файл с расширением `.gen` (вместо `.nes`)
  для игр Genesis-раздела; остальной пайплайн (`store_install`, дедуп имени, авто-подтяжка
  метаданных постфактум) переиспользуется без изменений, просто параметризуется
  `platform`/секцией.

## Main Screen: фильтр платформы

Переключатель-кнопки «NES» / «Genesis» (как в Store, не выпадающий список) — рядом с
существующим фильтром режима игры (`filterMode`, [screens.md](screens.md#1-main-screen)).
Оба фильтра комбинируются (AND) при построении `filteredGames`. Игры без явного выбора
(«обе платформы сразу») не предусмотрены — ровно одна платформа активна за раз, как и в
Store.

## Метаданные

`metadata/scraper.rs::fetch_metadata` сейчас жёстко ищет по `NES_SECTION_ID`. С
добавлением `Game.platform` поиск метаданных выбирает `SECTION_ID` по платформе игры —
тот же `GENESIS_SECTION_ID`, что заведён для Store выше (один и тот же раздел сайта
обслуживает и поиск ROM'ов, и метаданные, как уже устроено для NES). Парсинг
описания/обложки/`player_mode` (селекторы `.ftext > p`, `.ss-area img`, `.finfo li`)
предполагается платформенно-независимым (общий шаблон страницы сайта) — требует проверки
на реальной странице Genesis-игры при реализации.

## Save state

`SaveState.file_path` сейчас — конкретно jsnes-формат (`nes.toJSON()` как JSON). С двумя
движками формат становится непрозрачным для остального кода: `EmulatorCore.saveState()`
отдаёт `Blob` в собственном формате движка (для Genesis — что бы ни отдавало выбранное
WASM-ядро), лаунчер хранит его как есть по тому же пути
`<app-data>/saves/<game_id>/slot_<n>.json`
(имя файла не привязано к формату, менять не обязательно), не пытаясь понять/сконвертировать
содержимое. `SaveState` в БД не получает нового поля — платформа игры и так известна из
`Game.platform`, этого достаточно, чтобы выбрать правильный движок для `loadState`.

## Netplay (кооп)

Кооп для Genesis — часть этой задачи (не отложено). Сейчас `src/netplay/engine.ts` жёстко
завязан на внутренности jsnes: создаёт `NES` напрямую, сам вызывает `nes.frame()`,
переиспользует `jsnes/src/browser/screen.js`/`speakers.js` (см.
[netplay.md](netplay.md#почему-нельзя-переиспользовать-jsnes-browser)). Лок-степ протокол
сам по себе (буферизация ввода, `INPUT_DELAY_FRAMES`, `NetplayMessage`) платформо-агностичен
— завязка только в месте, где движок непосредственно продвигается на кадр и куда пишутся
кнопки. План: `NetplayEngine` принимает движок через тот же интерфейс `EmulatorCore`, что и
`EmulatorScreen` (выше), вместо прямого импорта `jsnes`; `setButtonState`/кадровый advance
дергаются через него для обоих игроков, как сейчас `nes.buttonDown/buttonUp`/`nes.frame()`.
Требования протокола не меняются — оба пира всё так же должны независимо владеть ROM с
одинаковой SHA-256 (сверяется в `Handshake`), только теперь ROM может быть `.gen`, а не
только `.nes`. Genesis-контроллер (3 или 6 кнопок, см. выше) кодируется в `Input.buttons`
вместо текущего NES-специфичного 1-байтового битового поля — потребует расширения формата
сообщения (например, отдельный `platform`/более широкий `buttons`, чтобы вместить больше
кнопок, чем NES-байт) — уточнить точный формат при реализации.
