# Мультиплатформенность: Sega Genesis (.gen)

**Статус: эмуляция, магазин, настройка управления, `Game.platform` в БД и фильтр Main
Screen реализованы** — можно добавить `.gen` через «Добавить игры»/сканирование
библиотеки или найти/установить прямо из `Store Screen` (переключатель «NES»/«Genesis»,
второй раздел emu-land.net), запустить игру (движок, видео, аудио, ввод, save state в
`Emulator Screen`), переназначить клавиатуру/геймпад для обоих игроков на
`Settings Screen` → «Эмулятор» → переключатель «Genesis» (см. «Контроллер» ниже) и
отфильтровать библиотеку по платформе на `Main Screen` тем же переключателем-кнопками.
**Остальное — метаданные по названию, кооп — ещё спланировано, не реализовано** и
помечено «планируется» здесь и в перекрёстных ссылках из
[architecture.md](architecture.md), [data-model.md](data-model.md),
[screens.md](screens.md), [netplay.md](netplay.md).

## Идентификация платформы

`Game.platform` (`"nes" | "genesis"`, реализовано) — источник истины на бэкенде для уже
установленных игр, но не единственное место, которое знает о платформе: до того, как файл
ROM попадёт в библиотеку, платформа всё ещё определяется по месту, которому это нужно:

- `src-tauri/src/db/mod.rs::platform_for_rom_path` — вычисляет `platform` по расширению
  `rom_path` (`.gen` → `"genesis"`, иначе `"nes"`) и записывает его в `insert_game_if_missing`
  (добавление игры) и `update_game_rom` (смена версии из магазина); источник истины в БД,
  используется фильтром `Main Screen` (см. ниже). Только `.gen` — без `.md`/`.bin`/`.smd`
  (расширенная поддержка форматов — отдельная задача, если понадобится).
- `src-tauri/src/commands/library.rs::is_supported_rom` — какие расширения вообще
  принимаются при сканировании папки и ручном добавлении файла (`.nes`, `.gen`).
- `src/screens/EmulatorScreen/index.tsx` — `const isGenesis = game.romPath.toLowerCase().endsWith(".gen")`,
  переключает движок/раскладку/save-state кодек; не читает `Game.platform` напрямую (то же
  расширение, дублирование ради простоты — экран и так уже смотрит на `romPath` для других
  нужд).
- `src/screens/StoreScreen/index.tsx` — здесь платформа не выводится из файла (ROM'а на
  диске ещё нет, только предстоит скачать), а явно выбирается пользователем через
  переключатель «NES»/«Genesis» и прокидывается параметром `StorePlatform` во все
  Store-команды (`store_search`/`store_browse`/`store_list_files`/`store_install`, см.
  «Store Screen» ниже) — решение задачи «платформу нужно знать до того, как файл ROM
  появится на диске» через явное UI-состояние, а не через БД.

Существующие записи `Game` при миграции на новую версию БД получают `platform = "nes"` по
умолчанию (`add_column_if_missing` в `src-tauri/src/db/mod.rs`, по образцу `player_mode`)
— корректно для всех, кто пользовался лаунчером до появления Genesis (только `.nes`).

Платформозависимый поиск метаданных по названию (см. «Метаданные» ниже) на `Game.platform`
пока не завязан — там всё ещё отдельная задача.

## Движок эмуляции (реализовано)

NES работает через [jsnes](https://github.com/bfirsh/jsnes) — JS-библиотека прямо в webview,
без Rust-эмуляции (`Browser` из пакета монтируется в `EmulatorScreen`, ROM-байты читает
Rust-бэкенд и просто отдаёт во фронтенд). Genesis — тем же путём: WASM-ядро
[genesis_plus_gx](https://github.com/ekeeke/Genesis-Plus-GX) (libretro-порт того же ядра,
что в RetroArch) в браузере, без нативной эмуляции на Rust-стороне.

**Выбранный пакет: [`romdev-core-gpgx`](https://www.npmjs.com/package/romdev-core-gpgx)**
(часть проекта [romdev](https://github.com/monteslu/romdev)) — публикует только сырой
Emscripten-артефакт ядра (`genesis_plus_gx_libretro.js` + `.wasm`), без обвязки. Это было
осознанным выбором **против** двух других рассмотренных вариантов:

- **EmulatorJS** — готовый цельный веб-плеер (своё меню, свой конфиг геймпада, свой save
  state UI), а не управляемый класс — не даёт пошагово вызывать один кадр эмуляции извне,
  что обязательно для будущего лок-степ кооп-нетплея (см. «Netplay» ниже), и конфликтует с
  уже существующим UI `Emulator Screen` (свой оверлей/слоты). Плюс GPL-3.0 на сам плеер.
- **`romdev-core-host`** (обвязка того же romdev-проекта, дала бы готовый `LibretroHost` с
  `stepFrames`/`setInput`/`serializeState`) — отклонена: её скомпилированный код
  разбросанно дёргает `await import("node:fs/promises")` и подобные Node-only импорты,
  которые ломают продакшен-сборку Vite (Rollup пытается статически резолвить их для
  браузерного бандла). Вместо неё — собственная, компактная (~250 строк) реализация
  публичного libretro callback API (`src/emulator/genesis/callbacks.ts`, `framebuffer.ts`),
  портированная и адаптированная под TS из `romdev-core-host/callbacks.js`+`framebuffer.js`
  (MIT), но без Node-зависимостей и без ненужного для genesis_plus_gx кода (proxied-ядра,
  HW-render, C64-специфика).

**Лицензия ядра**: Genesis Plus GX распространяется под non-commercial лицензией (см.
`node_modules/romdev-core-gpgx/README.md`) — свободно для личного/некоммерческого
использования, запрещает перепродажу. Это ограничение самого движка (не пакета), значимо
только если лаунчер когда-либо станет коммерческим.

**Node → браузер патч**: `genesis_plus_gx_libretro.js` собран с Emscripten-флагом
`ENVIRONMENT_IS_NODE=true` захардкоженным — без патча webview падает на
`await import("module")`. Патч (`patches/romdev-core-gpgx+0.14.0.patch`, тот же
`patch-package`-механизм, что и у `patches/jsnes+2.1.0.patch`) меняет флаг на `false`;
поскольку `GenesisCore.create()` (см. `src/emulator/genesis/GenesisCore.ts`) сам скачивает
`.wasm` через `fetch` и передаёт байты модулю как `wasmBinary` (минуя emscripten-овский
`readBinary`/`readAsync`, которые под `-sENVIRONMENT=node` вообще не собраны для браузера),
остальной код глея не тронут и корректно работает — проверено и под Node (симулированная
браузерная загрузка через явный `wasmBinary`), и вживую в браузере (Chromium через
`agent-browser`, страница гоняла ядро с синтетическим ROM: кадры, звук, save state).

### Диспетчеризация в Emulator Screen (реализовано, без формального интерфейса)

`EmulatorScreen` не получил общий интерфейс движка (`EmulatorCore`) — вместо этого прямое
ветвление по `isGenesis` внутри тех же эффектов, что уже занимались jsnes: отдельная ветка
монтирует `<canvas>` вручную, гоняет `requestAnimationFrame`-цикл (`core.frame()` +
`core.getFrameRgba()` → `ctx.putImageData`), проигрывает звук через `AudioBufferSourceNode`
(накопительное планирование по `audioCtx.currentTime`), слушает клавиатуру/геймпад с
фиксированной раскладкой (см. «Контроллер» ниже) и делает save state через
`core.serializeState()`/`unserializeState()`. `fitScreenPixelPerfect` обобщена на
параметры `(stage, width, height)` вместо захардкоженных NES-констант — Genesis обычно
320×224, но может быть 256×192 (H32-режим), берётся из `GenesisCore.width/height` после
разгонных кадров в `loadRom()`.

Пропущенный сейчас формальный `EmulatorCore`-интерфейс — осознанное упрощение (YAGNI, две
ветки читаемее преждевременной абстракции с одним реальным потребителем на каждую), но его,
скорее всего, придётся ввести, когда дойдёт очередь до кооп-нетплея для Genesis (см. ниже) —
`NetplayEngine` тогда получит вторую реализацию движка тем же способом.

## Контроллер (реализовано)

NES-раскладка (8 экшенов: `UP/DOWN/LEFT/RIGHT/A/B/SELECT/START`, 2 игрока) не покрывает
Genesis-пад. Решение — отдельный набор экшенов на платформу, а не расширение общего:

- **NES** (без изменений): `UP/DOWN/LEFT/RIGHT/A/B/SELECT/START`.
- **Genesis** — 3-кнопочный пад: `UP/DOWN/LEFT/RIGHT/A/B/C/START` (`GenesisActionName` в
  `src/utils/genesisControls.ts`; `GenesisButtons` в `GenesisCore.ts` — те же поля в
  нижнем регистре, `EmulatorScreen` переводит между ними по карте
  `GENESIS_ACTION_TO_KEY`). 6-кнопочный пад (доп. `X/Y/Z/MODE`) — опциональное расширение
  позже, не блокирует первую версию.
- Клавиатура (оба игрока) и геймпад (оба игрока, по порядку подключения) переназначаются
  на `Settings Screen` → «Эмулятор» → переключатель «Genesis» (см. ниже), тем же способом,
  что и NES-раскладка — читаются из `localStorage` при монтировании `EmulatorScreen`
  (`getGenesisCodeBasedKeyMap`/`getGenesisGamepadButtonMaps`), переназначение подхватывается
  со следующего захода на экран эмулятора. `GenesisCore.setInput(port, buttons)` принимает
  полное состояние пада за раз (не down/up-события, как `nes.buttonDown/buttonUp`), поэтому
  и клавиатурный обработчик, и опрос геймпада в `EmulatorScreen` сами держат текущее
  состояние кнопок по игроку.
- Ключи `localStorage` — **не** `keyboard_controls_nes`/`keyboard_controls_genesis`, как
  изначально прикидывалось (переименовывать уже существующий плоский NES-ключ
  `keyboard_controls` не стали — риск ради чистой симметрии не оправдан, никакой миграции
  существующих пользовательских раскладок не требовалось). Вместо этого — новые отдельные
  ключи только для Genesis: `keyboard_controls_genesis` (`src/utils/genesisControls.ts`),
  `gamepad_controls_genesis` (`src/utils/genesisGamepad.ts`). NES-ключи (`keyboard_controls`,
  `gamepad_controls`) не тронуты.
- Дефолтная раскладка клавиатуры Игрока 2 для Genesis — новая (в исходной константе
  `EmulatorScreen` раньше поддерживался только Игрок 1 с клавиатуры): W/A/S/D — d-pad,
  G/H/J — A/B/C, Space — Start (по аналогии с тем, как NES-раскладка Игрока 2 продолжает
  WASD вправо по клавиатуре под кнопки).

### Ремаппинг стиков и аналоговых триггеров (RT/LT) (реализовано)

Биндинг геймпада (`GamepadBinding`/`GenesisGamepadBinding`, теперь общий тип `GamepadSource`
в `src/utils/gamepadInput.ts`) — не просто индекс кнопки, а `{ type: "button"; buttonId }` или
`{ type: "axis"; axisId; direction: 1 | -1 }`. На любое действие (в том числе A/B/C/Start, не
только направления) можно назначить не только физическую кнопку, но и отклонение оси —
стика или, если конкретный геймпад репортит их как оси, а не как `buttons[6]/[7]`, триггеров
RT/LT. Ось переводится в дискретное нажатие по порогу `AXIS_THRESHOLD = 0.5` (та же константа,
что уже использовалась для стика в меню-навигации и netplay) через `isAxisPressed`.

- **UI ремаппинга** (`EmulatorTab.tsx`) — во время ожидания входа опрашивает и `pad.buttons`,
  и `pad.axes`; первое, что пересекло порог с прошлого кадра (`findNewlyPressedButton`/
  `findNewlyCrossedAxis`), становится новым биндингом. Подпись в UI — `describeGamepadSource`
  (кнопки — по стандартным позициям Xbox/PS-раскладки, оси — «Левый/Правый стик ←/→/↑/↓» или
  «Ось N +/−» для нестандартных).
- **Инжекция в игру** (`EmulatorScreen.tsx`, оба gameplay-поллинга) и **netplay**
  (`src/netplay/localInput.ts`) читают уже не плоскую `Map<buttonIndex, action>`, а
  `{ buttons, axes }` (`GamepadBindingMaps`/`GenesisGamepadBindingMaps`) и обрабатывают оси
  тем же способом, что и кнопки — с отдельным диффом предыдущего кадра на игрока, чтобы
  посылать `buttonDown`/`buttonUp` только на переходах (NES) или пересобирать полное
  состояние каждый кадр (Genesis, `core.setInput`).
- Старые сохранённые в `localStorage` раскладки (формат `{ buttonId }` без поля `type`)
  нормализуются на лету при чтении (`normalizeGamepadSource`) — миграция не нужна.
- Левый стик как D-pad в меню-навигации (`useSpatialNavigation.ts`) и как дефолт в netplay
  (`localInput.ts`) остаётся отдельным нередактируемым поведением "из коробки", не связанным
  с пользовательским ремаппингом конкретных действий.

## Settings Screen: переключатель nes/gen (реализовано)

Внутри вкладки «Эмулятор» (`EmulatorTab.tsx`) — верхний переключатель-кнопки «NES» /
«Genesis» (тот же визуальный стиль `.tabs`/`.tabButton`, что у подвкладок «Клавиатура»/
«Контроллер» ниже), под которым показываются настройки соответствующей платформы:

- **Общее** (не зависит от платформы): громкость (`Settings.volume` — общий на все
  платформы, отдельной per-platform громкости нет).
- **Платформо-зависимое**: подвкладки «Клавиатура»/«Контроллер» показывают набор экшенов
  активной платформы (NES: 8 кнопок; Genesis: 3-кнопочный набор выше — по 2 игрока в обоих
  случаях), читают/пишут в соответствующий платформенный ключ `localStorage`. Компонент
  дублирует состояние/эффекты (`listeningFor`/`listeningForGamepad` для NES,
  `listeningForGenesis`/`listeningForGenesisGamepad` для Genesis) параллельно, а не через
  общую параметризованную реализацию — та же простота, что и в диспетчеризации движка в
  `EmulatorScreen` (см. выше): два явных набора состояний читаемее преждевременной
  генерализации, когда потребителей всего два. «Сбросить по умолчанию» действует на
  активную платформу+вкладку независимо от остальных трёх комбинаций.

## Store Screen: фильтр и источник для Genesis (реализовано)

- **UI**: переключатель-кнопки «NES» / «Genesis» над алфавитными вкладками (тот же паттерн
  держим в уме для `Main Screen`, см. ниже) — определяет, в каком разделе искать/листать и
  какое расширение ожидается при установке. Задизейблен, пока открыта любая модалка
  экрана (список файлов/выбор папки/подтверждение замены версии) — переключение платформы
  посреди уже открытого диалога создало бы рассинхрон между тем, что показано, и тем, что
  реально установится.
- **Источник**: второй раздел на [emu-land.net](https://www.emu-land.net/) — id и путь
  проверены вживую (curl'ом) тем же способом, что и `NES_SECTION_ID`/`ROMS_PATH` в своё
  время: страница `/consoles/genesis/roms/<letter>` содержит форму «Поиск в разделе» с
  `<input type="hidden" name="id" value="39">`. `StorePlatform` (enum в
  `src-tauri/src/store/scraper.rs`) инкапсулирует пару `(SECTION_ID, ROMS_PATH,
  расширение)` на платформу и приходит явным параметром Tauri-команд
  (`store_search`/`store_browse`/`store_list_files`/`store_install`) — не глобальная
  константа, как раньше, а значение текущего переключателя с фронтенда. `GENESIS_SECTION_ID
  = "39"` заведён в `store/scraper.rs` (не в `metadata/scraper.rs`, где живёт
  `NES_SECTION_ID`) — поиск метаданных по названию платформозависимым пока не стал, см.
  «Метаданные» ниже.
- Установка из магазина берёт из архива первый файл с расширением `.gen` (вместо `.nes`)
  для игр Genesis-раздела (`extract_rom_from_zip`, переименован из `extract_nes_from_zip`,
  принимает расширение параметром) — проверено вживую скачиванием реального архива,
  внутри действительно `.gen`, не `.md`/`.bin`. Остальной пайплайн (`store_install`,
  дедуп имени, авто-подтяжка метаданных постфактум через `game_page_url(slug, platform)`)
  переиспользуется без изменений, просто параметризуется `platform`.
- «Игра уже установлена» (сверка по названию для предложения «сменить версию») теперь
  также проверяет платформу по расширению `rom_path` — иначе NES- и Genesis-игра со
  случайно совпадающим названием предлагались бы на замену друг другу.
- Живые тесты (`cargo test -- --ignored`, `store::scraper::tests::*_genesis_*`) гоняют
  поиск/просмотр/список файлов/скачивание/метаданные против реального Genesis-раздела —
  зеркало уже существовавших NES-тестов, все проходят.

## Main Screen: фильтр платформы (реализовано)

Переключатель-кнопки «NES» / «Genesis» (как в Store, не выпадающий список,
`src/screens/MainScreen/index.tsx`, стили `.platformToggle`/`.platformButton` в
`MainScreen.module.css`) — рядом с существующим фильтром режима игры (`filterMode`,
[screens.md](screens.md#1-main-screen)). Оба фильтра комбинируются (AND) при построении
`filteredGames` — фильтрация по `game.platform === platformFilter` на клиенте (без
похода в БД, `list_games` и так возвращает все поля). Игры без явного выбора («обе
платформы сразу») не предусмотрены — ровно одна платформа активна за раз, как и в Store;
по умолчанию открывается «NES». Задизейблен, пока идёт загрузка библиотеки или открыта
любая модалка экрана — тот же паттерн, что у остальных элементов шапки.

## Метаданные

`metadata/scraper.rs::fetch_metadata` (поиск игры по названию — используется на вкладке
«Метаданные» в Settings Screen кнопкой «Обновить») сейчас жёстко ищет по
`NES_SECTION_ID`, платформу игры не учитывает. С добавлением `Game.platform` поиск
метаданных должен выбирать `SECTION_ID` по платформе игры — `GENESIS_SECTION_ID` для
этого уже существует (заведён в `store/scraper.rs` для Store, см. выше), нужно будет
сделать его доступным и для `metadata/scraper.rs` (например, переместить туда, как
`NES_SECTION_ID`, раз он станет нужен в обоих местах).

Сам факт, что парсинг страницы игры (`.ftext > p`/описание, `.ss-area img`/обложка,
`.finfo li`/«Игроки:») платформенно-независим — общий шаблон сайта, один и тот же код
парсит и NES-, и Genesis-страницы — **уже подтверждён**: `fetch_metadata_by_url`
переиспользуется установкой из Store для автозагрузки метаданных сразу после установки
Genesis-игры (см. выше), и живой тест `genesis_game_page_url_yields_parseable_metadata`
гоняет её против реальной страницы `/consoles/genesis/roms/aladdin` — проходит. Не хватает
только платформенного выбора `SECTION_ID` в самом поиске по названию (`find_game_url`).

## Save state (реализовано)

`SaveState.file_path` для NES — конкретно jsnes-формат (`nes.toJSON()` как JSON). Формат
Genesis-снимка (`retro_serialize`, ~1МБ бинарного блоба — полное состояние 68000/Z80/VDP/
PSG/YM2612) полностью отличается и остаётся непрозрачным для бэкенда: `EmulatorScreen`
кодирует его в base64 (`genesisStateToBase64`/`genesisStateFromBase64` в `GenesisCore.ts`,
чанками по 32КБ — иначе `String.fromCharCode(...bigArray)` падает на лимите аргументов) и
шлёт той же командой `save_state(gameId, slot, data: string)`, что и NES — бэкенд как хранил
произвольную строку файлом на диске, так и хранит, никаких изменений в
`src-tauri/src/commands/saves.rs`/`db` не понадобилось. `SaveState` в БД не получил нового
поля — платформа определяется по `isGenesis` в `EmulatorScreen` (см. «Идентификация
платформы» выше), этого достаточно, чтобы выбрать правильный кодек при загрузке слота.

## Netplay (кооп) — спланировано, не реализовано

Явно вынесено за рамки первой версии эмуляции (см. «Явные ограничения» в начале файла) —
`EmulatorScreen` сейчас показывает ошибку, если открыть кооп-сессию для Genesis-игры
(`netplay && isGenesis` в основном эффекте), вместо попытки скормить Genesis ROM в
NES-движок. `GenesisCore.frame()`/`setInput()` уже имеют ровно ту пошаговую форму (один
кадр за вызов, явное состояние пада), которая нужна лок-степ-движку — технической
блокировки для последующей интеграции нет, просто не сделано в этом заходе.

Сейчас `src/netplay/engine.ts` жёстко завязан на внутренности jsnes: создаёт `NES` напрямую, сам вызывает `nes.frame()`,
переиспользует `jsnes/src/browser/screen.js`/`speakers.js` (см.
[netplay.md](netplay.md#почему-нельзя-переиспользовать-jsnes-browser)). Лок-степ протокол
сам по себе (буферизация ввода, `INPUT_DELAY_FRAMES`, `NetplayMessage`) платформо-агностичен
— завязка только в месте, где движок непосредственно продвигается на кадр и куда пишутся
кнопки. План: `NetplayEngine` дублирует для Genesis то же ветвление, что уже есть в
одиночной игре (см. «Диспетчеризация в Emulator Screen» выше) — `GenesisCore.frame()`/
`setInput()` вместо прямого импорта `jsnes`, вызываемые для обоих игроков так же, как
сейчас `nes.buttonDown/buttonUp`/`nes.frame()`. Если к этому моменту ветвлений накопится
достаточно (одиночная игра + кооп, каждая на 2 платформы), может иметь смысл наконец
формализовать общий интерфейс движка вместо копирования `isGenesis`-веток — решать по
факту, а не заранее.
Требования протокола не меняются — оба пира всё так же должны независимо владеть ROM с
одинаковой SHA-256 (сверяется в `Handshake`), только теперь ROM может быть `.gen`, а не
только `.nes`. Genesis-контроллер (3 или 6 кнопок, см. выше) кодируется в `Input.buttons`
вместо текущего NES-специфичного 1-байтового битового поля — потребует расширения формата
сообщения (например, отдельный `platform`/более широкий `buttons`, чтобы вместить больше
кнопок, чем NES-байт) — уточнить точный формат при реализации.
